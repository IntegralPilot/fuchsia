# Fuchsia local testing skill (`fx test`)

This skill provides the ability to run Fuchsia local tests directly using the
`fx test` command, saving structured test logs and artifacts to a known
temporary location, and using `jq` and `ffx debug symbolize` to efficiently
extract and analyze failures.

## Workflow

### 1. Discover, select, and add tests to the build
To find and configure tests in the build system:

#### A. Discover tests with `fx search-tests`
Use `fx search-tests` to perform heuristic searches for test names. The output
will display matches and provide the exact command to add them to your build:
```bash
fx search-tests <query>
```

#### B. Dry-run selections with `fx test --dry`
To see which test suites match your current selection without executing them:
```bash
fx test <selection> --dry
```

#### C. List individual test cases with `fx test --list`
To list all individual test cases within matching suites and see the exact `fx`
command needed to run each one individually:
```bash
fx test <selection> --list
```

> [!NOTE]
> The `--list` flag requires a target device or running emulator since listing
> test cases happens on-device for device-targeted tests.

#### D. Add a test to your build
If a test is not currently in your build configuration, add it:
```bash
fx add-test //path/to/test:target_name
```

### 2. Run the test and save outputs
Run the test directly using `fx test`. Always specify a temporary directory
under `out/` to store logs and output artifacts, and use the `--simple` flag to
minimize console verbosity.

Define a unique temporary run directory and an empty subfolder for artifacts:
```bash
TEST_RUN_DIR="out/tmp_test_runs/run_$(date +%s)"
mkdir -p "$TEST_RUN_DIR/out"
```

Then run `fx test` directing the log and output directory there:
```bash
fx test <test_name_or_selector> --simple --outdir "$TEST_RUN_DIR/out" --logpath "$TEST_RUN_DIR/log.json.gz" [extra_flags]
```

> [!IMPORTANT]
> The log path specified by `--logpath` must be located **outside** the
> directory specified by `--outdir` (for example, in the parent directory).
> If the log file is created inside `--outdir` before testing starts, `fx test`
> will error, complaining that the output directory already exists and is not
> empty.

#### Common extra flags
- `--no-build`: Skip the incremental build phase if you are positive the binary
  is already up-to-date.
- `--test-filter <pattern>`: Run specific test cases within a test suite (for
  example, `--test-filter "hello_tests::my_test"`).
- `--count <number>`: Execute each test case multiple times (ideal for
  reproducing flaky test behaviors).
- `-f` or `--fail`: Stop executing immediately after the first failed test
  suite.
- `--min-severity-logs <level>`: Modify minimum log severity level emitted by
  components during the test (for example, `--min-severity-logs DEBUG`).

### 3. Decompress the event log
The structured event log file generated by `--logpath` is compressed with gzip.
Decompress it for analysis:
```bash
gzip -cd "$TEST_RUN_DIR/log.json.gz" > "$TEST_RUN_DIR/log.json"
```

### 4. Process and analyze test results
Use the following `jq` recipes to inspect the test run events in `log.json`:

#### A. List all executed suites and their statuses
```bash
jq -s 'group_by(.id)[] | {name: (map(.payload.test_suite_started.name) | map(select(. != null)) | .[0]), status: (map(.payload.test_suite_ended.status) | map(select(. != null)) | .[0])} | select(.name != null)' "$TEST_RUN_DIR/log.json"
```

#### B. Find only failed test suites
```bash
jq -s 'group_by(.id)[] | {name: (map(.payload.test_suite_started.name) | map(select(. != null)) | .[0]), status: (map(.payload.test_suite_ended.status) | map(select(. != null)) | .[0])} | select(.name != null and .status == "FAILED")' "$TEST_RUN_DIR/log.json"
```

#### C. Extract and symbolize output (stdout/stderr) of failed suites
This query locates the child execution tasks of any failed suites and retrieves
their stdout/stderr stream, piping it to `fx ffx debug symbolize` to resolve
any backtraces automatically:
```bash
jq -r -s '
  (map(select(.payload.test_suite_started != null)) | map({key: (.id|tostring), value: .payload.test_suite_started.name}) | from_entries) as $suite_names |
  (map(select(.payload.test_suite_ended.status == "FAILED")) | map({key: (.id|tostring), value: true}) | from_entries) as $failed_suites |
  (map(select(.payload.program_execution != null and ($failed_suites[.parent|tostring] == true))) | map({key: (.id|tostring), value: .parent}) | from_entries) as $exec_parents |
  (map(select(.payload.program_output != null and ($exec_parents[.id|tostring] != null)))) as $outputs |
  ($outputs | group_by(.id))[] |
  (.[0].id | tostring) as $exec_id |
  ($exec_parents[$exec_id] | tostring) as $suite_id |
  $suite_names[$suite_id] as $suite_name |
  "#### Suite: \($suite_name)\n\n```\n" + (map(.payload.program_output.data) | join("")) + "\n```\n"
' "$TEST_RUN_DIR/log.json" | fx ffx debug symbolize
```

#### D. Read on-device test cases summary (when available)
For on-device or component tests, `fx test` writes a `run_summary.json` file
inside the output directory. If that file exists, you can extract the test cases
summary directly:
```bash
jq -r '.data.suites[] | "* Suite: \(.name) (\(.outcome))\n" + (.cases[] | "  - \(.name) (\(.outcome))")' "$TEST_RUN_DIR/out/run_summary.json"
```

### 5. Clean up temporary files
After completing your analysis and extracting any needed information, remove
the temporary directory to keep the workspace clean:
```bash
rm -rf "$TEST_RUN_DIR"
```
