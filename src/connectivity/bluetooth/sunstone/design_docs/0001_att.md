# Objective

Migrate the Attribute Protocol (ATT) stack from the legacy Pigweed C++
implementation (`pw_bluetooth_sapphire/host/att`) to a modern, type-safe, and
memory-safe Rust library in `sunstone/sapphire-gatt`.

This document serves as the global architectural layout and core requirements
outline for the ATT stack in Rust.

# Background

The Sapphire Bluetooth team is systemically migrating its legacy C++ stack to
Rust to eradicate memory corruption vulnerabilities and enforce architectural
safety invariants. The stack supports the Android runtime environment and is
designed to be embedded-friendly to provide a platform-independent solution for
teams outside of rvos.

The current Fuchsia Bluetooth Stack (Sapphire) is implemented in C++. The
**Sunstone** project is the official initiative to rewrite Sapphire in Rust. As
the baseline transport foundation for profile-level and GATT communications, the
**Attribute Protocol (ATT)** must be migrated first to unlock downstream layers.

In C++, the ATT subsystem was designed under a **callback-based API** (storing
dynamic closures that capture raw pointer references inside attributes,
introducing heavy lifetime hazards and heap wrapping overheads). In Sunstone,
the ATT layer is redesigned from the ground up in Rust to provide a safe,
asynchronous, and zero-allocation transport foundation suitable for embedded
(`no_std`) environments.

# Requirements

## Functional Requirements

- **Concurrent Client/Server Operation**: The stack must support operating
  simultaneously as an ATT Client and an ATT Server over a single logical link.
  This allows the local device to discover and query remote profile services
  while concurrently serving local characteristics (e.g. Battery Service, Device
  Info) to the connected peer.
- **Transaction Flow Control & Response Matching**: The stack must enforce
  strict request-response matching and sequential flow control. Only one
  sequential request transaction may be in flight at a time, ensuring that
  inbound responses are matched strictly against the active outgoing request.
- **Dynamic MTU Negotiation & Enforcement**: The stack must actively negotiate,
  map, and enforce packet payload limits using the Exchange MTU transaction
  sequence. All outbound and inbound packet boundaries must be verified against
  this negotiated MTU (ranging from 23 to 512 bytes) to prevent runtime packet
  fragmentation under L2CAP.
- **Complete Attribute Protocol Coverage**:
  - _Discovery_: Support range mapping (Find Information) and UUID filtering
    (Find By Type Value) to build attribute maps.
  - _Reading_: Support standard attribute reads (Read Request), segmented long
    reads (Read Blob), and batch discovery reads (Read By Type/Group Type).
  - _Writing_: Support acknowledged writes (Write Request), unacknowledged
    commands (Write Command), and transactional two-phase writes
    (Prepare/Execute).
  - _Events_: Support server-initiated notifications and flow-controlled (locked
    transaction) indications.
- **Decoupled Transport Abstraction**: The protocol rules engine must be
  completely decoupled from the underlying L2CAP transport layer. It must expose
  clean asynchronous boundaries (traits) allowing it to work seamlessly with
  either our test-only mock loopback link or real target hardware L2CAP links.
- **Security & Permission Enforcement**: The ATT Server must evaluate security
  access requirements (encryption, authenticated pairing, authorization, and key
  size bounds) against link properties on query ingress, instantly rejecting
  non-compliant queries with spec-mandated error PDUs.

## Non-Functional Requirements

- **Bare-Metal Portability (`no_std` Invariant)**: The core Attribute Protocol
  (ATT) stack must not depend directly on the standard library (`std`),
  floating-point runtimes, or target OS-specific primitives (such as Zircon
  socket handles or Zircon status values). It must compile cleanly on a `no_std`
  target.
- **Zero-Allocation Memory Safety**: The packet parsing, composition, and
  serialization engine must execute with zero runtime allocations. Network
  frames (PDUs) must be represented as safe, layout-validated zero-copy views
  over existing transport buffers, eliminating memory copying and heap
  allocation entirely during network processing.

# Non-Requirements

- **Implementing GATT Profiles**: While `sapphire-gatt` will house the ATT
  database, implementing GATT features (such as remote client cache management
  or Service/Characteristic profile definition hooks) is strictly out of scope.
- **Link-Layer State Management**: The ATT layer does not track target
  advertising, scanning, or logical connection handshakes; these are managed
  exclusively by GAP and L2CAP managers.
- **Production `Database` & `Attribute` Implementations**: Implementing the
  production `no_std` attribute database (which organizes service hierarchies,
  manages dynamic handles, and tracks characteristic groups) and concrete
  attribute representations is strictly out of scope for this document. These
  will be specified in the GATT layer design document. The ATT layer provides
  only stateless protocol routing logic, the abstract traits (`Database` and
  `Attribute`), and in-crate mocks (`MockDb` and `MockAttribute`) for test
  verification.
- **Multithreading**: The entire ATT and GATT connection transaction loop
  operates strictly within a single, dedicated execution thread context.
  Supporting parallel multi-threaded task scheduling or thread pools would not
  be feasible.

# Design

## Architectural Overview

To achieve zero-allocation memory safety and embedded (`no_std`) compatibility,
the Sunstone ATT design departs from the C++ architecture in two fundamental
ways:

- **Async Execution Model**: Rather than storing dynamic closures and callbacks
  that capture heap pointers, the ATT Client and Server operate using native
  **async Rust**. Reads, writes, and protocol transactions are modeled as
  **stack-allocated futures**, shifting session state and flow control entirely
  onto the local async task context.
- **Zero-Allocation Database Representation**: Rather than relying on a
  heap-allocated hierarchy of service groups with self-referential pointers, the
  ATT layer accesses attributes directly by handle through the `Database` and
  `Attribute` traits.

## System Block Architecture

The ATT stack is implemented as a no-cost library, avoiding inter-process
message passing and bridging queues. Protocol state is tracked per-connection
(per peer link): for each connected remote peer, the upper `GATT` layer
instantiates, owns, and executes an independent `ATT Client`, `ATT Server`, and
`BearerRouter` bound to that connection's fixed L2CAP channel:

```
+-----------------------------------------------------------------------------------------+
|                       GATT Layer Task Context (Per-Connection)                          |
|                          (Local Device Memory; Out of Scope)                            |
|                                                                                         |
|  +-----------------------------------------------------------------------------------+  |
|  |                           ATT Protocol Rules Engine                               |  |
|  |                             (sapphire-gatt::att)                                  |  |
|  |                                                                                   |  |
|  |  +-----------------------------------+     +-----------------------------------+  |  |
|  |  |            ATT Client             |     |            ATT Server             |  |  |
|  |  |         (att/client.rs)           |     |         (att/server.rs)           |  |  |
|  |  |                                   |     |                                   |  |  |
|  |  | - Drives outbound transactions    |     | - Processes inbound requests      |  |  |
|  |  | - [ Direct Async Method Calls ]   |     | - [ Direct Database Calls ]       |  |  |
|  |  +-----------------------------------+     +-----------------------------------+  |  |
|  |       |                    ^                    ^                    |            |  |
|  |       | (Outbound          | (Inbound           | (Inbound           | (Outbound  |  |
|  |       |  BearerTx)         |  RxHandle)         |  RxHandle)         |  BearerTx) |  |
|  |       |                    |                    |                    |            |  |
|  |       |               +----+--------------------+----+               |            |  |
|  |       |               | BearerRouter (att/router.rs) |               |            |  |
|  |       |               | - Demultiplexes by Opcode    |               |            |  |
|  |       |               +------------------------------+               |            |  |
|  |       |                                 ^                            |            |  |
|  +-------|---------------------------------|----------------------------|------------+  |
+----------|---------------------------------|----------------------------|---------------+
           | (Outbound PDUs)                 | (Inbound PDUs)             | (Outbound PDUs)
           v                                 |                            v
+-----------------------------------------------------------------------------------------+
|                                        L2CAP                                            |
+-----------------------------------------------------------------------------------------+
```

### Complete ATT Packet Flow

The ATT layer encapsulates all wire-protocol rules, MTU bounds, opcode
demultiplexing, and L2CAP fixed channel (`CID 0x0004`) I/O, providing a clean
separation of concerns:

1. **Inbound Demultiplexing (`L2CAP -> BearerRouter -> ATT Client / Server`)**:
   All incoming ATT frames from the remote peer arrive over L2CAP and are passed
   into `BearerRouter` (`sapphire-gatt::att::router`). `BearerRouter` inspects
   the PDU opcode and demultiplexes frames into independent `BearerRxHandle`
   receiver queues via `RouteFilter`:
   - **`RouteFilter::Requests`**: Matches client request opcodes (`ReadReq`,
     `WriteReq`, `ExchangeMtuReq`, etc.) -> routed to `Server::run` /
     `Server::handle_request`.
   - **`RouteFilter::Responses`**: Matches server response opcodes (`ReadRsp`,
     `WriteRsp`, `ExchangeMtuRsp`, etc.) -> routed to `Client` transaction
     procedures.
   - **`RouteFilter::ServerEvents`**: Matches unsolicited server events
     (`HandleValueNtf`, `HandleValueInd`) -> routed to `ServerEventStream`.
   - **`RouteFilter::Confirmations`**: Matches confirmations (`HandleValueCnf`)
     -> routed to `Server` indication handlers.

2. **Outbound Direct Transmission (`ATT Client / Server -> L2CAP`)**: Outbound
   packets do not pass through `BearerRouter`. Both `Client` and `Server` hold
   cloned `BearerTx` handles that write directly to the underlying L2CAP fixed
   channel:
   - **`Server -> L2CAP`**: When `Server::handle_request` finishes evaluating an
     attribute query (or when sending a Notification/Indication via
     `notify`/`indicate`), it serializes the outbound Response or Event PDU onto
     the stack and transmits it directly over L2CAP by calling
     `self.bearer_tx.send(packet).await`.
   - **`Client -> L2CAP`**: When `Client` initiates a procedure (e.g.,
     `read_by_type`, `write`, `exchange_mtu`) or automatically acknowledges an
     Indication (`HandleValueCnf`), it serializes the Request or Confirmation
     PDU and transmits it directly over L2CAP via
     `self.bearer_tx.send(packet).await`. In both cases, `BearerTx` enforces
     negotiated ATT MTU boundaries before pushing frames onto the wire.

3. **GATT Interaction Boundary**: During active operation, the upper GATT layer
   never interacts directly with L2CAP. Communications between GATT and ATT
   operate exclusively as **type-safe async method calls** and **await
   boundaries** on `Client` and `Server`, utilizing L2CAP solely for
   over-the-air payload streaming with the peer.

## Mapped Primitives and Types

The ATT stack relies on common Bluetooth Low Energy primitives defined in helper
crates:

- **`PeerId`** (`sapphire-common`): A type-safe wrapper representing a unique
  64-bit remote peer identifier.
- **`Uuid`** (`sapphire-common`): A type-safe representation of a Bluetooth SIG
  standard 16-bit UUID or a 128-bit vendor-specific UUID.

## Packet Serialization & Emboss Views

ATT packet layouts, opcodes, error codes, and headers are defined using Emboss
schemas, generating zero-copy view wrappers that validate buffer boundaries and
provide structured field accessors without heap allocation:

- **Fixed-Size Frames & Headers**: Fixed request and response structures map
  directly to generated Emboss views over stack-allocated buffers.
- **Compile-Time Typestates**: View wrappers transition from `UncheckedState` to
  `CompleteState` upon validation (`check_complete()`), providing infallible
  field accessors without runtime bounds checks or `.unwrap()` calls.
- **Variable-Length Response Lists**: Discovery procedures returning lists of
  entries (such as Find Information, Read By Type, and Read By Group Type) are
  processed through zero-allocation borrowed iterators. This decouples dynamic
  packet slicing from higher GATT layers and avoids hardcoding byte offsets in
  consumer code.

## Traits

Many aspects of the ATT implementation rely on trait definitions for the
underlying attribute and database implementations, enabling delegation of
concerns to the upper layers.

### The `Attribute` Trait

```rust
use crate::att::pdu::ErrorCode;
use sapphire_common::{PeerId, Uuid};

pub trait Attribute {
    /// The type UUID representing the meaning of this attribute.
    fn uuid(&self) -> &Uuid;

    /// Initiates a read action, writing a chunk of populated bytes starting at `offset` into `buf`.
    ///
    /// Note: `buf` uses `&mut [u8]` rather than `MaybeUninit<u8>` to guarantee
    /// API memory safety and keep Profile-layer implementations entirely `unsafe`-free.
    async fn read_chunk(
        &self,
        peer_id: PeerId,
        offset: u16,
        buf: &mut [u8],
    ) -> Result<usize, ErrorCode>;

    /// Initiates an atomic write of a chunk of data starting at `offset`.
    async fn write_chunk(
        &self,
        peer_id: PeerId,
        offset: u16,
        data: &[u8],
    ) -> Result<(), ErrorCode>;

    /// Returns the ending handle of the group if this attribute is a group declaration.
    fn group_end_handle(&self) -> Option<u16> {
        None
    }
}
```

## Attribute Database Specifications

Migrating the legacy C++ object-oriented grouping relational graph directly to
Rust presents significant friction. The C++ pattern relies on self-referential
structures (an `Attribute` references back to its owning parent
`AttributeGrouping`, and registers closures that capture raw C++ `this` pointer
references), violating the Rust borrow checker's single-ownership rules and
lifetime constraints.

### Decision: Associated-Type Generics (No Type Erasure)

To avoid dynamic heap allocations and virtual dispatch overhead, the design
declares the concrete database using an **associated type**
(`type Attr: Attribute` on the `Database` trait). This decouples the ATT layer
from the concrete database collection and attribute storage, allowing the ATT
server and transaction tests to run against `MockDb` while GATT later supplies
the production database and attribute representations.

#### The Database Trait

The ATT protocol requires only two basic functional operations from the
underlying attribute database registry: a way to retrieve a single attribute
over its unique 16-bit handle, and a way to retrieve ranges of attributes
sequentially in handle-sorted order. The abstract `Database` trait models these
minimal operations directly, enabling delegation of concerns to the upper
layers:

```rust
use crate::att::AttributeHandle;

pub trait Database {
    /// The concrete type resolving to our dynamic Attributes.
    type Attr: Attribute;

    /// Searches for an attribute in the database matching the handle.
    fn find_attribute(&self, handle: AttributeHandle) -> Option<&Self::Attr>;

    /// Queries an inclusive range of attributes (`start..=end`) in handle-sorted order.
    fn query_range(
        &self,
        start: AttributeHandle,
        end: AttributeHandle,
    ) -> impl Iterator<Item = (AttributeHandle, &Self::Attr)>;
}
```

This minimal API is fully sufficient to satisfy the entire ATT protocol rules
engine's routing and discovery needs without requiring dynamic allocations.

### Active Transaction Query Routing

Under this associated-type architecture, the stateless `att::Server` executes
peer transaction requests sequentially with absolute zero memory allocations:

```
[ Peer Link Bearer ]             [ att::Server Loop ]             [ DB: Database ]                  [ Attr: Attribute ]
         |                                |                                |                                |
         | ---- Inbound Request PDU ----> |                                |                                |
         |      (Zero-copy packet view)   |                                |                                |
         |                                | -- find_attribute(handle) ---> |                                |
         |                                |    (Handle lookup)             |                                |
         |                                | <--- returns &Attr ----------- |                                |
         |                                |                                                                 |
         |                                | -- Evaluate static UUID getter -------------------------------> |
         |                                |    (Statically dispatched method)                               |
         |                                |                                                                 |
         |                                | -- read_chunk(peer_id, offset, &mut buf) ---------------------> |
         |                                |    (Statically sized Stack Future)                              |
         |                                |                                                                 |
         |                                | <================ Await Sequential Future ====================> |
         |                                |                                                                 |
         |                                | <---------------- returns Ok(written_len) --------------------- |
         |                                |                                                                 |
         | <--- Send Outbound Reply PDU - |                                                                 |
         |      (Pack value from stack)   |                                                                 |
         v                                v                                v                                v
```

As shown above, the transaction flow operates in five discrete stages:

1. **PDU Decoding**: The `Server` receives an inbound packet from the bearer and
   validates it through a zero-copy Emboss view without heap allocation.
2. **Handle Lookup**: The server queries the generic database instance via
   `Database::find_attribute` (or `Database::query_range` for discovery
   requests) to obtain a reference `&Attr` to the matching attribute.
3. **Attribute Evaluation**: The server evaluates attribute properties (such as
   checking `attr.uuid()` for permissions or discovery constraints) using static
   dispatch.
4. **Asynchronous Execution**: For read or write requests, the server awaits the
   attribute's `read_chunk` or `write_chunk` future sequentially on the stack.
5. **Response Serialization**: The result bytes are serialized into an Emboss
   response view and transmitted back across the bearer link.

## Alternative Designs Evaluated

### 1. Closed Enum Dispatch (`AttributeType`)

Evaluating a closed `AttributeType` dispatcher enum inside the ATT crate mapping
specialized concrete implementations such as `StaticAttribute`,
`AsyncAttribute`, and `BroadcastAttribute` reveals two critical concerns:

1. **Unnecessary ATT Layer Complexity**: The ATT stack only provides generic
   stateless transaction validation and handle-based range queries. It does not
   need to understand or distinguish between static values, dynamic async
   callbacks, or broadcast properties. The categorization and management of
   different attribute types belong entirely to the GATT layer. Defining them in
   ATT violates layer boundaries.
2. **Useless for Verification**: In-crate unit testing (like client/server
   transaction loops) only requires verifying that queries route and evaluate
   correctly. A single generic `MockAttribute` that tracks a UUID is completely
   sufficient to verify all protocol behaviors. Implementing specialized
   production attribute types inside ATT added compile-time complexity without
   providing any testing utility.

### 2. The Trait Object Model (`dyn Attribute`)

Evaluating a type-erased **Trait Object Model (`&dyn Attribute`)** to solve
parent-child pointer conflicts in Rust by wrapping async methods inside pinned,
boxed future trait objects (e.g. `BoxFuture` / `LocalBoxFuture`) reveals three
critical flaws:

1. **Dynamic Heap Allocation on Hot Path**: Calling `attribute.read()` requires
   a **heap-allocated future (`Box::pin`) on every transaction request**,
   introducing runtime overhead.
2. **Startup Allocation Bloat**: Inserting attributes into containers required
   wrapping them inside `Box<dyn Attribute>` pointers.
3. **Virtual Dispatch Overhead**: Every read, write, handle, and UUID getter
   invoked at runtime required a vtable lookup, reducing CPU efficiency.

### Testing Mock Implementations (`MockAttribute` and `MockDb`)

The ATT layer defines the `Attribute` and `Database` traits, but does not
provide their production implementations, which are handled by the GATT layer.

For in-crate unit and integration testing of ATT transaction loops, the codebase
provides lightweight test utilities (`MockAttribute` and `MockDb`):

- **`MockAttribute`**: An in-memory implementation of the `Attribute` trait
  backed by an owned vector (`StdVec<u8>`). It provides constructors for
  standard and grouped attributes (`new`, `new_grouped`) and allows test cases
  to inject synthetic write failures via `set_write_error`.
- **`MockDb`**: A test database implementation storing attributes in an
  `alloc::collections::BTreeMap<AttributeHandle, MockAttribute>` to provide
  sorted range queries (`query_range`), lookup by handle (`find_attribute`), and
  handle-range existence checks (`has_attributes_in_range`).

# Core Specifications

### ATT Client / Server Handshake

- **Opcodes**: Exchange MTU Request (`0x02`), Exchange MTU Response (`0x03`),
  Error Response (`0x01`).
- **Negotiation Algorithm**: When the handshake completes, both peers set their
  negotiated MTU to `max(kLEMinMTU(23), min(client_rx_mtu, server_rx_mtu))`.
- **Fallback Security**: If legacy endpoints reject handshakes with
  `RequestNotSupported`, the client recovers, locks in default MTU, and proceeds
  to avoid termination.

### Handle Discovery

- **Opcodes**: Find Information Request (`0x04`), Find Information Response
  (`0x05`), Find By Type Value Request (`0x06`), Find By Type Value Response
  (`0x07`).
- **Procedure**:
  - _Find Information_: Maps target range handles, returning lists of
    handle/UUID associations (supporting 16-bit and 128-bit mappings).
  - _Find By Type Value_: Locates handles matching a targeted type UUID and
    value array (commonly used to look up Service Definitions matching targeted
    UUID constraints).

### Reading Attributes

- **Opcodes**: Read Request (`0x0A`), Read Response (`0x0B`), Read Blob Request
  (`0x0C`), Read Blob Response (`0x0D`), Read By Type Request (`0x08`), Read By
  Type Response (`0x09`), Read By Group Type Request (`0x10`), Read By Group
  Type Response (`0x11`).
- **Procedure**:
  - _Read Request_: Fetches raw data from handle.
  - _Read Blob_: Reads long attributes (>MTU size) by specifying dynamic data
    byte offsets.
  - _Read By Type/Group_: Queries handles based on UUID class classification,
    returning paired lists containing start/end boundaries.

### Writing Attributes

- **Opcodes**: Write Request (`0x12`), Write Response (`0x13`), Write Command
  (`0x52`), Prepare Write Request (`0x16`), Prepare Write Response (`0x17`),
  Execute Write Request (`0x18`), Execute Write Response (`0x19`).
- **Procedure**:
  - _Write Request / Response_: Acknowledged write verification loop.
  - _Write Command_: Fire-and-forget unacknowledged, high-throughput writes (no
    flow-control response, silent server discard on parameters mismatch).
  - _Prepare / Execute Write_: Client packages long writes into offset-mapped,
    uncommitted queue slots. Executing the execute command commits them
    atomically or cancels all.

#### Transactional Prepare Write Queue Design

The transactional prepared writes queue is mapped locally on the `Server` using
a length-prefixed `PrepareQueue<S: StorageFamily>` backed by a contiguous
`Vec<u8, S>` (bound to `ArrayStorage<SIZE>` for zero-allocation embedded
targets).

If storage capacity is exhausted (OOM), `PrepareQueue::try_push` rolls back
partial writes and returns `PrepareError::QueueFull`, which the server maps to
the spec-mandated `ErrorCode::PREPARE_QUEUE_FULL` (`0x09`) error response.

A dedicated RAII draining iterator (`PrepareQueueDrain`) executes queued writes
and clears storage automatically on drop to ensure atomic cleanup on error.

### Server Events

- **Opcodes**: Handle Value Notification (`0x1B`), Handle Value Indication
  (`0x1D`), Handle Value Confirmation (`0x1E`).
- **Procedure**:
  - _Notification_: Server fires unacknowledged state updates to subscribed
    client CCCDs. High throughput, no confirmation response needed.
  - _Indication_: Server pushes state updates and **blocks** further
    transactions until the client returns a baseline confirmation packet,
    enforcing strict transaction order checks.
  - _Unified Client Stream (`ValueStream`)_: On the client side, both
    Notifications and Indications are consumed through a single, unified
    `ValueStream` yielding a `ValueUpdate` enum (`Notification` or
    `Indication`). When `.next().await` receives an Indication (`0x1D`), it
    automatically transmits `HandleValueConfirmation` (`0x1E`) down the
    underlying bearer before yielding the item to the caller. This single-stream
    design eliminates application-level `select!` loops, avoids cancellation
    hazards, and requires only one stack buffer in client application loops.

# Implementation Plan & Roadmap

## ATT Client / Server Handshake

- **Subtask 1 [Done]**: Define the asynchronous `L2capChannel` interface
  boundary and Channel Ids.
- **Subtask 2 [Done]**: Zero-Copy ATT PDU Definitions.
  - Defines packed structural formats for MTU Request, Response, and Error
    Response frames.
  - Implements type-safe ingress validation using Emboss views and compile-time
    typestates to reject invalid opcodes and short buffers at the parsing
    boundary.
  - Includes a test suite verifying parsing, serialization, and error
    conversions.
- **Subtask 3 [Done]**: Stateless Bearer Core.
  - Implement stack-allocated, split `BearerTx` and `BearerRx` endpoint wrappers
    over L2CAP.
  - Retain absolute zero-allocation context (bypassing `extern crate alloc` or
    `Arc` reference sharing in this phase).
  - Define an in-memory `MockChannel` (mock `Tx` and `Rx` types implementing
    L2CAP traits) to enable local standalone verification.
- **Subtask 4 [Done]**: Handshake Engine, Domain Primitives, & In-Crate
  Verification.
  - Define the type-safe `PeerId` domain primitive representing a unique 64-bit
    identifier for a remote peer.
  - Implement `Client::exchange_mtu` doing a direct sequential
    request-and-await. The transaction await future must resolve on receiving
    either the expected `ExchangeMTUResponse` PDU OR an `ErrorResponse` PDU
    target-matched to the MTU request, preventing deadlocks on error/fallback
    paths.
  - Implement `Server::handle_handshake` doing an in-place request-parsing and
    response-reply transaction.
  - Include a cooperative asynchronous in-crate unit test running the Client and
    Server MTU handshake over our `MockChannel` test harness and verifying
    correct negotiation.

## Emboss Migration

Following initial protocol bringup, all handwritten zerocopy packet structures
will be migrated to generated Emboss views and typestates:

- **Single Source of Truth**: Replaces manually duplicated struct definitions
  with shared Emboss schema files, ensuring bit-for-bit protocol consistency
  across C++ and Rust implementations.
- **Declarative Validation**: Eliminates manual offset arithmetic and
  boilerplate validation logic in favor of declarative schema constraints.
- **Compile-Time Typestates & Zero-Overhead Access**: Integrates compile-time
  typestate tracking to shift struct layout validation from runtime to compile
  time. Once verified, packet views allow infallible reads and writes with
  guaranteed memory safety and zero bounds-checking runtime overhead.

# Backwards Compatibility

- **Packet-Level Integrity**: All zero-copy packet structures are layout-checked
  bit-for-bit against legacy C++ packed structs.
- **Fallback Behaviors**: If legacy servers reject MTU exchange procedures with
  `RequestNotSupported`, our client must safely recover, configure a 23-byte
  fallback parameter, and bypass abort actions.

# Testing

Our verification strategy prioritizes fast local feedback, complete bare-metal
target checking, and highly robust fuzzing validation:

- **Unit Testing**:
  - Implemented and run on the host target for every single development
    requirement to verify localized module functionality, mock loopback
    networks, and error mappings.
  - Ensures that local edits remain highly tested and verified in real-time
    under a sub-second developer feedback loop.
- **Property-Based Testing (Proptest)**:
  - Leveraged standard in Fuchsia to execute automated high-chaos input boundary
    and state validation.
  - **Framework for Proptest Selection**: Rather than testing simple, fixed-size
    protocol steps, property-based tests are deployed strategically on
    dynamically complex boundaries. Writing proptests is highly appropriate in
    the following three scenarios:
    1. **Untrusted Boundary Ingress (Input Parsers)**: When parsing
       variable-length binary payloads, packed headers, or list maps from
       untrusted external sources (such as remote peer links). Proptests
       generate a high-chaos input space of byte sequences to prove the decoder
       **never panics, crashes, or triggers out-of-bound indexing errors** on
       malformed inputs.
    2. **Dynamic Offset and Segmentation Decoders**: When calculating slice
       index offsets, dynamic page limits, or data segmentation boundaries based
       on user-provided offsets (e.g., paging long attribute value reads across
       multiple MTU limits). Proptests verify that any random combination of
       payload lengths, MTU bounds, and byte offsets remains strictly
       boundary-safe without underflows or overflows.
    3. **Stateful Transactional State-Machines**: When validating the
       concurrency boundaries, state locks, queue commits, and atomic rollback
       guarantees of stateful routers (e.g., executing prepared writes
       transactional queues, or connection-level event indication locks).
       Stateful proptests run a chaotic, random sequence of valid and invalid
       state transitions to prove the system **never deadlocks, always maintains
       atomic rollback consistency, and leaks no memory.**
- **Hardware Verification**:
  - Once lower layers are implemented, integration will be verified against
    target hardware. Until then, hardware testing is deferred.

# Security & Privacy

- **Input Sanitization**: Emboss view constructors and completeness checks
  (`check_complete()`) verify buffer bounds and schema constraints before
  accessors transition to `CompleteState`. This prevents buffer overflow,
  underflow, and malformed payload vulnerabilities.
- **No Interior Mutability**: Core packet structures derive the static
  `Immutable` marker, preventing concurrent read/write state corruptions in
  multi-threaded execution runtimes.

# Future Work

The following Attribute Protocol procedures and requests are out of scope for
the initial baseline ATT migration and are deferred to future milestones:

- **Multiple Attribute Reads**:
  - _Read Multiple Request (`0x20`) / Response (`0x21`)_: Reading a list of
    fixed-length attribute values in a single round-trip transaction.
  - _Read Multiple Variable Request (`0x22`) / Response (`0x23`)_: Reading a set
    of variable-length attribute values returned with length prefixes.
- **Signed Write Operations**:
  - _Signed Write Command (`0xD2`)_: Authenticated, unacknowledged writes
    verifying a 12-byte Authentication Signature (MAC) calculated with the
    Connection Signature Resolving Key (CSRK) over unencrypted links.
- **Transaction Timers (30-Second Spec Timeout)**:
  - Enforce the Bluetooth Core Spec mandated 30-second transaction timeout on
    in-flight client requests and server indications, aborting transactions and
    terminating the bearer link if the peer fails to respond within the window.
